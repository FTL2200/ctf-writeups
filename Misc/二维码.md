## 三、解题过程

### 3.1 阶段一：附件解压与初步识别

**操作**

```bash
# 解压附件
7z x f4571698-e6e4-41b6-8853-2aab17cef02a.zip
```

**结果**

- 解压得到 `QR_code.png`，文件大小 **672 字节**，尺寸 280×280。
- 将 `.png` 直接以图片方式打开，显示为一个标准二维码。

**分析结论**

> 770 字节的压缩包解压出 672 字节的图片，压缩比异常（图片本应远大于压缩包），说明压缩包内仅有一个极小文件，或图片本身经过高度压缩/裁剪。此处暂不做结论，继续向下分析。

### 3.2 阶段二：二维码内容识别

**操作**

使用手机扫码或在线工具（草料二维码 `cli.im`、ZXing `zxing.org/w/decode.jspx`）识别二维码。

**结果**

```
secret is here
```

**分析结论**

- 二维码本身结构完整、可正常识别，**不存在**「二维码损坏 / 缺定位角 / 高度被截断」等问题。
- 识别结果 `secret is here` 并非 Flag，而是一条**提示信息**，指向「秘密存在于别处」。
- 由此排除「二维码解码类」题型的可能性，转向文件层面的隐写分析。

### 3.3 阶段三：常规隐写排查（排除法）

**操作**

依次使用常规图片隐写检测手段：

```bash
# 元数据检查
exiftool QR_code.png

# LSB 隐写检查
zsteg -a QR_code.png

# 文件头信息
strings -a QR_code.png | grep -iE 'flag|secret|\{'
```

同时排查两方面：

1. **图片宽高篡改**：使用 PNG 宽高修复工具（修改 IHDR 中的宽/高字段）——结果无隐藏区域。
2. **文件末尾附加数据**：未在常规隐写工具中体现。

**结果**

- 元数据无异常。
- LSB 各通道无有效数据。
- 宽高修改后无新增可见区域。

**分析结论**

> 常规隐写工具无果，说明秘密不在「像素数据」或「元数据」中，需要检查**文件结构本身**。

---

### 3.4 阶段四：文件结构分析（关键突破）

**操作**

使用 010 Editor 打开 `QR_code.png`，定位文件尾部。

**结果**

```text
001C0h:  ... 00 00 00 00 00 49 45 4E 44 AE 42 60 82 | 50 4B 03 04 14 00 09 00 ...
                                          ↑ IEND  ↑ CRC    ↑ PK 本地文件头
```

关键观察：

- `49 45 4E 44` 即 ASCII 字符串 **`IEND`**，是 PNG 文件的标准结束标记。
- `AE 42 60 82` 是 `IEND` 块对应的 CRC32 校验值，即 `IEND` 块的完整结尾。
- `IEND` 之后紧跟 `50 4B 03 04`，即 ASCII **`PK\x03\x04`**，是 **ZIP 本地文件头**的标志。

**分析结论**

> 该 PNG 文件在 `IEND` 结束标记之后，**追加了一个完整的 ZIP 压缩包**，属于典型的「图片 + 压缩包」双文件拼接（Polyglot File）手法。
>
> 由于 PNG 解析器遇到 `IEND` 即停止解析，后续的 ZIP 数据不会影响图片正常显示，因此常规看图手段无法发现。

### 3.5 阶段五：提取嵌套 ZIP

**方法一：使用 7-Zip 直接提取**

```bash
7z x QR_code.png
```

7-Zip 能够识别 PNG 尾部附加的 ZIP 数据并直接提取。

**方法二：使用 010 Editor 手动截取**

1. 定位 `PK\x03\x04` 起始偏移（本例为 `0x1D4`）。
2. 从该字节选中至文件末尾。
3. 右键 → `Save Selection As...` → 保存为 `secret.zip`。

**结果**

提取得到 `secret.zip`，内含单个文件 **`4number.txt`**（原始大小 15 字节，压缩后 29 字节）。

### 3.6 阶段六：加密方式判定

打开 `secret.zip` 时提示需要密码。此时需先判断加密类型。

#### 3.6.1 检查 ZIP 加密标志位

ZIP 的本地文件头结构如下：

```text
偏移    长度    字段
0x00    4      签名 50 4B 03 04
0x04    2      解压所需版本
0x06    2      通用标志位（General Purpose Bit Flag）
0x08    2      压缩方法
...
```

**通用标志位**的第 0 位（bit 0）为 **1** 表示「文件已加密」。

本例中，`PK\x03\x04` 之后的标志位为：

```text
14 00 | 09 00 | 08 00
        ↑ 标志位 = 0x0009（bit0=1，bit3=1）
```

#### 3.6.2 尝试「伪加密」修复

**原理**：伪加密是指攻击者/出题人仅修改了 ZIP 头部的加密标志位，而**数据本身并未加密**。此时将标志位改回 `00 00` 即可正常解压，无需密码。

**操作**（010 Editor）：

1. 定位本地文件头：`PK\x03\x04` 后第 6–7 字节，将 `09 00` 改为 `00 00`。
2. 定位中央目录：搜索 `PK\x01\x02`，其后第 8–9 字节，同样变为 `00 00`。
3. `Ctrl+S` 保存。

> 注意：ZIP 结构中共有两处加密标志位（本地文件头 + 中央目录），**必须同时修改**。

**结果**

解压时提示：

```
数据错误：4number.txt
```

**分析结论**

> 修复标志位后仍无法正常解压，说明**并非伪加密**，而是真正的 ZipCrypto 加密。

---

### 3.7 阶段七：加密类型确认（压缩率判据）

**关键指标**：

| 指标 | 数值 |
| --- | --- |
| 原始大小（decmplen） | 15 字节 |
| 压缩后大小（cmplen） | 29 字节 |
| **压缩率** | **193%** |

**分析结论**

> 正常 deflate 压缩的压缩率应显著小于 100%。本例压缩后体积**大于**原始体积（193%），这是数据已被加密的典型特征：
>
> - 加密后的数据熵接近最大值，压缩算法对其完全无效；
> - 再加上压缩流头部与尾部开销，导致体积膨胀。
>
> 因此可确定：**该文件使用 ZipCrypto 传统加密，必须爆破或还原密码。**

### 3.9 阶段九：密码爆破

#### 方式一：Python（推荐，零依赖）

```python
import zipfile

zf = zipfile.ZipFile("secret.zip")

for i in range(10000):
    pw = f"{i:04d}".encode()
    try:
        data = zf.read("4number.txt", pwd=pw)
        print(f"[+] 密码: {pw.decode()}")
        print(f"[+] 内容: {data}")
        break
    except Exception:
        continue
```

**运行结果**：

```
[+] 密码: 7639
[+] 内容: b'CTF{vjpw_wnoei}'
```

耗时约 **0.15 秒**。

#### 方式二：hashcat（GPU 加速）

**步骤 1：提取 hash**

```powershell
cd "D:\John\john-1.9.0-jumbo-1-win64\run"
.\zip2john.exe "D:\hashcat\hashcat-8.0.0\secret.zip" | Out-File -FilePath hash.txt -Encoding ascii
```

输出示例：

```
ver 2.0  secret.zip/4number.txt  PKZIP Encr: cmplen=29, decmplen=15, crc=AE4C3446
secret.zip/4number.txt:$pkzip2$1*1*2*0*1d*f*ae4c3446*0*29*8*1d*ae4c*508b*...*$/pkzip2$:4number.txt:secret.zip::D:\...\secret.zip
```

**步骤 2：清洗 hash（仅保留核心 hash 串）**

hashcat 只识别 `$pkzip2$...$/pkzip2$` 部分，需去除前后缀：

```powershell
$raw = Get-Content hash.txt -Raw
$m = [regex]::Match($raw, '\$pkzip2\$.*?\$/pkzip2\$')
$m.Value | Set-Content hash.txt -Encoding ascii -NoNewline
```

**步骤 3：执行爆破**

```powershell
.\hashcat.exe -m 17200 -a 3 "路径\hash.txt" ?d?d?d?d --force
```

参数说明：

| 参数 | 含义 |
| --- | --- |
| `-m 17200` | PKZIP（传统加密）哈希模式 |
| `-a 3` | 掩码（Mask）攻击模式 |
| `?d?d?d?d` | 4 位数字掩码 |
| `--force` | 忽略驱动兼容性检查（Intel 核显必需） |

**运行结果**：

```
Status...........: Cracked
Hash.Mode........: 17200 (PKZIP (Compressed))
$pkzip2$1*1*2*0*1d*f*ae4c3446*0*29*8*1d*ae4c*508b*...*$/pkzip2$:7639
Recovered........: 1/1 (100.00%) Digests
Speed.#1.........: 5166.4 kH/s
```

两种方式结果一致：**密码为 `7639`**。

## 五、知识点总结

### 5.1 文件结构类

| 知识点 | 说明 |
| --- | --- |
| **PNG 结束标记** | `49 45 4E 44 AE 42 60 82`（`IEND` + CRC32） |
| **ZIP 本地文件头** | `50 4B 03 04`（`PK\x03\x04`） |
| **ZIP 中央目录** | `50 4B 01 02`（`PK\x01\x02`） |
| **ZIP 目录结束** | `50 4B 05 06`（`PK\x05\x06`，EOCD） |
| **Polyglot File** | 同一文件兼容多种格式，解析器遇到结束标记即停止，后续数据对前一格式不可见 |

### 5.2 加密判定类

| 判据 | 结论 |
| --- | --- |
| 标志位 `09 00` 但可正常解压 | 伪加密（改 `00 00` 即可） |
| 标志位 `00 00` 但解压报错 | 数据本身加密（真加密） |
| 压缩率 > 100% | 数据已加密（熵高，压缩无效） |
| 解压提示 `数据错误` / `CRC错误` | 密码错误或数据损坏 |

### 5.3 密码攻击类

| 策略 | 适用条件 | 工具 |
| --- | --- | --- |
| 伪加密修复 | 标志位异常 | 010 Editor |
| 掩码爆破 | 已知密码格式（如 4 位数字） | hashcat `-a 3` / Python |
| 字典攻击 | 密码为常见词 | hashcat `-a 0` + rockyou.txt |
| 明文攻击 | 已知压缩包内某文件内容 | bkcrack |
| CRC32 碰撞 | 待破解文件体积极小（≤ 6 字节） | 自定义脚本 |

## 六、技术要点详解

### 6.1 为什么常规隐写工具无法发现

本题的秘密**不存储在图片内容中**，而是以文件拼接的形式存在于 PNG 结束标记之后。

| 检测手段 | 检查对象 | 能否发现本题隐藏数据 |
| --- | --- | --- |
| ExifTool | 元数据段（EXIF/XMP） | 否 |
| zsteg / StegSolve | 像素最低有效位 | 否 |
| 宽高修复 | IHDR 宽高字段 | 否 |
| **十六进制编辑器查看文件尾** | **文件整体结构** | **是** |

**结论**：隐写分析应分为「内容层」与「结构层」两条路径。当内容层排查无果时，必须转向结构层分析。

### 6.2 ZIP 加密标志位的完整位置

ZIP 文件中有两处记录加密状态：

| 位置 | 偏移计算 | 本例值 |
| --- | --- | --- |
| 本地文件头 | `PK\x03\x04` 起始 + 6 | `0x1DA` |
| 中央目录 | `PK\x01\x02` 起始 + 8 | `0x239` |

**两处必须同时修改**，否则解压器可能从任意一处读取加密标志。

### 6.3 压缩率作为加密判据的可靠性

| 文件内容 | 压缩后大小 | 压缩率 | 结论 |
| --- | --- | --- | --- |
| 重复文本（如 1000 个 "A"） | 极小 | < 10% | 正常压缩 |
| 普通文本 | 略小 | 60-90% | 正常压缩 |
| **加密数据** | **变大** | **> 100%** | **加密** |

该判据在多道 CTF 压缩包题中均可作为快速判断依据。

## 七、踩坑记录

| # | 问题现象 | 原因 | 解决方案 |
| --- | --- | --- | --- |
| 1 | `cd /d` 报「找不到接受实际参数」 | `/d` 是 CMD 参数，PowerShell 不支持 | 使用 `cd "路径"` |
| 2 | `.\zip2john.exe` 报「无法识别」 | 当前工作目录未切换到 John 的 `run` 目录 | 先执行 `cd` |
| 3 | hashcat 报 `Byte Order Mark (BOM) was detected` | PowerShell 5.1 的 `>` 重定向默认输出 UTF-16 LE | 改用 `\| Out-File -Encoding ascii` |
| 4 | hashcat 报 `Signature unmatched` | `zip2john` 输出包含文件名前缀与路径后缀 | 正则提取 `$pkzip2$...$/pkzip2$` |
| 5 | hashcat 报 `No devices found/left` | 添加 `-D 1` 导致仅选择 CPU，而本机无 CPU 设备 | 移除 `-D 1`，或改用 `-D 2` |
| 6 | hashcat 8.0.0 报 `OpenCL kernel self-test failed` | Intel 核显驱动兼容性问题 | 换用 6.2.6，添加 `--force` |
| 7 | 修改标志位后仍提示需要密码 | 判断为真加密而非伪加密 | 确认压缩率 > 100% 后执行爆破 |
| 8 | 解压报「无法创建目标文件」 | Windows 资源管理器解压路径/权限问题 | 换用 7-Zip，或更换目标目录 |

## 八、同类题型扩展

### 8.1 出现频率较高的文件拼接组合

| 组合 | 识别方法 |
| --- | --- |
| PNG + ZIP | `IEND` 后出现 `PK\x03\x04` |
| JPG + ZIP | `FF D9` 后出现 `PK\x03\x04` |
| GIF + ZIP | `3B` 后出现 `PK\x03\x04` |
| PNG + 文本 | `IEND` 后出现可打印 ASCII |
| PNG + 另一张图 | `IEND` 后出现新的文件头 |

### 8.2 ZIP 密码题的一般处理顺序

```text
1. 尝试伪加密修复（改标志位）
        ↓ 失败
2. 查找密码线索（文件名、题面、图片内容、元数据）
        ↓ 无
3. 判断密码格式，选择攻击方式
   ├─ 已知格式 → 掩码爆破（-a 3）
   ├─ 常见密码 → 字典攻击（-a 0 + rockyou）
   ├─ 已知明文 → 明文攻击（bkcrack）
   └─ 体积极小 → CRC32 碰撞
```

### 8.3 常见哈希模式对照

| 文件类型 | hashcat `-m` | 提取工具 |
| --- | --- | --- |
| ZIP（传统加密） | 17200 | `zip2john` |
| ZIP（AES 加密） | 13600 | `zip2john` |
| RAR5 | 13000 | `rar2john` |
| RAR3 | 12500 | `rar2john` |
| 7z | 11600 | `7z2john.pl` |
| PDF | 10500 | `pdf2john.pl` |
| Office 2013+ | 9600 | `office2john.py` |
